=== WHAT'S ACTUALLY HAPPENING (mechanism, disclosed) ===
Decomposed exp-T3-trace-variant.run1.json's FunctionCall events by
functionName+url+line: 58,042 calls (7,835.8ms of the run's 8,262.04ms
FunctionCall total) are one minified function ("O") in a DIFFERENT chunk --
0xxxi2p_-v-e~.js (227,315 bytes, the largest chunk on the page). This is
NOT the blocked chunk and was flagged in the earlier S1 lens as "no string
match found for any named suspect component" -- an unattributed chunk. All
3 variant runs show the same function, same chunk, same order-of-magnitude
call count and duration (58,042/8262ms run1; comparable in run2/run3 by the
matching FunctionCall totals), i.e. this is a stable, reproducible failure
mode of blocking 14u.~01e7g0-p, not a one-off fluke.
exp-T3-block-request-count.mjs confirms the blocked chunk is requested
exactly ONCE per page load (matchCountTotal: 1) and aborts with
net::ERR_FAILED -- there is no network-level retry storm. The 58,042-call
loop is JS-side: something in the unrelated 227KB chunk spins tightly,
apparently reacting to the missing gsap/ScrollTrigger module (a poll/retry
loop waiting on a global or a ref that never initializes because the
blocked chunk's module evaluation never completes), rather than a request
being re-issued. Root-causing exactly which line in that chunk is doing
this is out of scope for this A/B pass (evidence only; would need reading
app/components source, which this phase forbids).
Separately, UpdateLayoutTree and Paint are literally 0 events (0.00ms) in
all 3 variant traces -- the page never re-lays-out or repaints anything for
the ~8.9s of the scroll window once the loop starts. This matches the
screencast: frameCount for the variant screencast run is 84 painted frames
over 9,156ms of wall time, versus 177 painted frames over 3,953ms for the
baseline screencast run -- roughly half the painted frames spread over
more than double the time. The page visually freezes while the CPU spins.

=== MOVEMENT vs NOISE FLOOR, PREDICTED DIRECTION ===
Predicted: all three trace totals and the >33ms frame share DROP; p95
interval stays low; colour switch reads smoother; offer-h2 time-to-visible
collapses (T1 cross-confirmation).
Actual, all 3 runs, same direction each time (fully reproducible, not
noise):
  UpdateLayoutTree: 483.68ms median -> 0.00ms median. Moved DOWN, but this
    is not "GSAP's layout cost removed" -- it is "nothing lays out or
    paints at all because the main thread is pinned by an unrelated loop,"
    which is a worse outcome, not a better one, and is not what the claim's
    own reasoning predicted (it predicted GSAP's specific layout-tree cost
    would disappear while normal scroll-driven layout continued).
  FunctionCall: 385.48ms median -> 8280.63ms median. Moved UP by ~21.5x,
    the opposite of predicted, on all 3 runs individually (8262/8289/8281
    all far above all 3 baseline values 385-397, no overlap whatsoever).
  EventDispatch: 328.61ms median -> 18.19ms median. Moved down, but for the
    same reason as UpdateLayoutTree (the main thread has no time left to
    dispatch/process events, not because GSAP's own event-handling cost
    was cleanly removed) -- consistent with the loop starving everything
    else, not a clean improvement.
  Frames >33ms: 46/290 (~15.9%) median -> 71/403 (~17.6%) median. Modest
    increase, wrong direction, though small relative to the other metrics.
  Frames >50ms: 0 median -> 70 median. 0 in every single baseline run ever
    captured in this pass (calibration + T1 + T2 + this baseline) vs ~70 in
    every single variant run -- an unambiguous, maximal-contrast movement
    in the WRONG direction, far beyond any noise floor (the noise floor for
    this metric, from every other measurement in this folder, is exactly
    0).
  World switches: 2 -> 0 on all 3 runs. The colour-switch mechanism does
    not merely "read smoother" under the block -- it stops firing
    altogether (per the JS instrument) while the screenshots show a harder,
    un-blended cut than baseline.
  Scroll wall time: ~3950-4460ms -> ~8910-8920ms, roughly doubled, and
    gestureCount stabilizes at 2 on all 3 variant runs (vs 1-2 in
    baseline) -- consistent with CDP command round-trips themselves being
    delayed by the pinned main thread.

VERDICT: not_causal.
The claim predicted that blocking the GSAP/ScrollTrigger chunk would
reduce main-thread cost during the scroll (UpdateLayoutTree, FunctionCall,
EventDispatch all down; frames >33ms down) and produce a smoother colour
switch. On all 3 runs, with the neutralizer re-confirmed valid against the
live deploy immediately before running, the metric did not move in the
predicted direction -- it moved sharply in the opposite direction on the
single largest and most decisive sub-metric (FunctionCall: ~21.5x UP, not
down; frames >50ms: 0 -> ~70, the starkest possible contrast given 0 is the
value every other measurement in this folder has ever produced for that
metric) and the colour-switch mechanism did not become smoother -- it
stopped firing as a JS-driven crossfade entirely, replaced by a harder,
un-blended cut in the screenshots. Per the task's own verdict rule
("'not_causal' if it does not move [in the predicted direction beyond
noise]"), this is a clean not_causal call: the metric moved, dramatically,
but away from the prediction, not toward it, consistently on all 3 runs.
This does not, by itself, refute the separate, already-established premise
that GSAP+ScrollTrigger consumes real main-thread time during normal
(unblocked) operation -- S1's read-only trace attribution and T1's own
CSS-only neutralizer (which left GSAP mounted and running, and cleanly
showed a ~30x improvement in the offer-heading metric with zero side
effects) already support that narrower premise on their own evidence. What
this experiment shows is that BLOCKING THE CHUNK OVER THE NETWORK -- the
specific neutralizer this claim proposed, and by extension "just strip
GSAP out" as a naive fix -- is not a clean way to test or realize that
premise on this live deploy: some other, unattributed chunk
(0xxxi2p_-v-e~.js) depends on the blocked chunk in a way that produces a
58,000-call retry/poll loop consuming 7.8+ of the scroll window's 8.9
seconds, freezes layout/paint entirely for that window, and disables the
world-switch crossfade rather than smoothing it. Any future fix aimed at
GSAP's scroll cost should follow T1's pattern (neutralize the visible
effect while leaving the module mounted, or make the removal conditional
in the actual source so the dependency in 0xxxi2p_-v-e~.js is resolved
correctly) rather than a network-level block -- but changing source is out
of scope for this evidence-only phase.
